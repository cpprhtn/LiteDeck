# 서버 모드 (웹 브라우저로 접근)

[← README](../README.md)

LiteDeck 을 데스크톱 앱 대신 **서버에 올려두고 브라우저로** 쓸 수 있습니다.
네이티브 바이너리를 못 까는 환경(정책상 실행 차단, 관리형 노트북 등)에서, 별도
서버 한 대에 올려두고 URL 로 접속하는 방식입니다 — 그라파나를 쓰는 모양과 같습니다.

```
브라우저 ──HTTP──▶ litedeck-server ──기존 SSH──▶ 관리할 서버들
```

데스크톱 앱과 **같은 코어**를 씁니다. 화면도 같습니다. 다른 것은 껍데기뿐입니다 —
Wails 웹뷰 대신 HTTP 로 UI 를 서빙하고, 웹뷰가 없어 **웹킷·GTK 의존이 없는 정적
단일 바이너리**입니다.

## 실행

```bash
# 리눅스 서버에서 (릴리스의 litedeck-server-linux-amd64)
./litedeck-server                       # 기본: 127.0.0.1:8765
./litedeck-server --addr 127.0.0.1:9000 # 포트 지정
```

띄운 뒤 브라우저로 그 주소를 엽니다. 서버·자격증명·연결은 데스크톱과 똑같이
동작합니다 — 호스트를 등록하고, 접속하고(호스트키·비밀번호는 브라우저 대화상자로
물어봅니다), 파일·터미널·모니터링·MCP 를 씁니다.

## 노출과 인증은 여러분 몫입니다

이 엔드포인트는 **여러분의 서버들에 SSH 세션을 엽니다.** 그 포트에 닿는 사람은
누구든 그 서버들을 다룰 수 있다는 뜻입니다. 그래서:

- **기본은 `127.0.0.1` 바인드.** 그대로면 서버 바깥에서 못 닿습니다.
- **바깥에 열려면 앞단에 리버스 프록시**(oauth2-proxy · Cloudflare Access ·
  Tailscale 등)를 두고 **거기서 인증·TLS 를 처리**합니다. LiteDeck 자체는 1인용을
  유지하고, 인증은 밖에 맡깁니다. 그라파나 실무 표준과 같습니다.

```nginx
# nginx 예시 — 인증(auth_request 등)은 여기서 걸고, LiteDeck 은 loopback 에
location / {
    proxy_pass http://127.0.0.1:8765;
    proxy_http_version 1.1;
    # WebSocket(이벤트·터미널·로그)을 위해
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    # 접속 프롬프트가 응답을 최대 몇 분 붙들 수 있으니 read timeout 을 넉넉히
    proxy_read_timeout 600s;
}
```

> [!IMPORTANT]
> 프록시 없이 바깥 주소로 바로 열려면(`--addr 0.0.0.0:...`) **`--token` 이
> 필수**입니다. 없으면 시작을 거부합니다 — 인증 없는 SSH 게이트웨이를 실수로
> 여는 것을 막기 위해서입니다.

## 비밀번호 (로그인)

서버 바이너리는 **로그인이 기본으로 켜져 있습니다.** 포트를 열면 로그인 페이지가
뜨고, 통과하면 세션 쿠키로 들어갑니다 — URL 토큰도 앞단 프록시도 없이(그라파나식).

- **기본 비밀번호는 `litedeck`** 입니다. 앱 이름 그대로 — 갓 띄운 인스턴스를 한
  번에 쓸 수 있게 한 기억용 기본값이지, 비밀은 아닙니다.
- **바꾸는 법은 배포 설정뿐입니다.** 웹에서는 못 바꿉니다(1인용이라 불필요하고,
  변경 폼은 공격 표면일 뿐). 터미널에서:
  ```bash
  # 환경변수로 (systemd 유닛·docker run·쉘 등)
  LITEDECK_PASSWORD='새-비밀번호' litedeck-server --self <user>
  # 또는 플래그로 (단, argv 는 ps 에 보이므로 환경변수를 권장)
  litedeck-server --password '새-비밀번호' ...
  ```
  바꾸려면 **그 설정을 고치고 재시작**합니다 — 그라파나·Cockpit 과 같은 방식.
- **기본값 그대로면 시작할 때 경고가 뜹니다.** 바깥에 노출하기 전에 꼭 바꾸세요 —
  `litedeck` 인 것을 아는 누구나 로그인할 수 있습니다.
- 로그인을 아예 끄려면 `--no-auth` (루프백 전용 — 비루프백 바인드에서는 거부).

## 알아둘 것 (검증 현황과 제약)

- **비밀번호가 네트워크로 나갑니다.** 헤드리스 서버에는 OS 키체인이 없어, 접속마다
  서버 비밀번호를 브라우저에서 물어봅니다. 그 값은 HTTP 로 서버까지 갑니다 — 순수
  loopback 이 아니라면 **반드시 TLS(프록시)** 뒤에 두세요. 평문 HTTP 로 바깥에 열면
  자격증명이 그대로 노출됩니다.
- **파일 업로드는 브라우저 파일 선택으로** 합니다(데스크톱의 네이티브 창 대신).
  고른 파일이 서버로 스트리밍돼 SFTP 로 원격에 쓰입니다. **폴더째 업로드와 드래그앤
  드롭, 원격→로컬 드래그**는 아직입니다 — 데스크톱 앱을 쓰세요.
- **1인용입니다.** 한 인스턴스는 한 사람의 세계입니다(호스트 목록·연결·Command Log
  가 하나). 여러 탭은 같은 상태를 공유합니다. 여러 명이 각자 로그인해 쓰는 멀티유저는
  범위 밖입니다 — 그건 다른 도구(Teleport·Warpgate 등)의 일입니다.
- **MCP 는 설정에서 켠 경우에만** 서버의 loopback 에 뜹니다(데스크톱과 동일).

## 검증

| | 상태 |
|---|---|
| **정적 빌드** | `CGO_ENABLED=0 GOOS=linux` 로 정적 ELF 바이너리 생성 확인 |
| **웹 전송 왕복** | 실 sshd 에 브라우저 접속 → 접속 프롬프트(호스트키·비밀번호)가 WS 로 뜨고 RPC 로 답해 핸드셰이크가 완료되는 것까지 통합 테스트로 확인 |
| **파일 업로드** | 실 sshd 로 연결한 뒤 브라우저 업로드가 원격에 정확히 쓰이는 것, 적대적 파일명이 폴더 밖으로 못 나가는 것까지 확인 |
| **UI 렌더** | 헤드리스 서버가 서빙하는 앱이 실제 브라우저에서 부팅·렌더되는 것 확인 |
| **실제 다중 사용자 부하** | 미검증 — 1인용 설계 |
| **리버스 프록시 뒤 배포** | 미검증 — 예시 설정은 위에 |

데스크톱 앱과 릴리스 절차는 [지원 범위](support.md)를 보세요.
