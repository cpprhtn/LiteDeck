# 지원 범위와 한계

[← README](../README.md)

무엇을 어디서 확인했는지, 그리고 이 도구가 적합하지 않은 환경과 지원하지 않는 기능을 적어둡니다.

**검증된 것과 검증되지 않은 것을 구분해서** 적습니다. 아래 "미검증"은 코드가 없다는 뜻이 아니라, 저자가 실제로 돌려보지 않았다는 뜻입니다.

| **경유 접속** | Alpine 컨테이너 2대 (경유 + 목적지) | ProxyJump. 목적지는 포트를 열지 않아 **직접 닿을 수 없는 상태**에서 확인 |

**실제 Linux SSH 서버는 위의 두 줄입니다.** Ubuntu 24.04.4 서버는 MCP 연동으로 조회 계통과 파일
읽기·쓰기·삭제까지 왕복했고, 라즈베리파이 4(Debian 12 · arm64)에서는 **GUI로 직접 쓰는 경로까지**
확인했습니다 — 서비스·컨테이너 제어, 파일 저장·삭제, **폴더째 전송과 이어받기**(한 전송을 두 번
끊었다 이어도), sudo 권한 상승 완료, 터미널 PTY, 실시간 로그 따라가기.

**명령 이력(sudo 저널)은 실기 저널로 확인했습니다.** Ubuntu 24.04 서버의 실제 `journalctl -t sudo`
출력을 파서에 그대로 먹여 19건을 읽었습니다 — 작업 디렉터리(`PWD=`) 추출, 거부된 시도와 실행된
명령의 구분, 효과 분류(변경/편집/조회)까지. 다만 **권한 세 갈래 중 「그룹에 없음」 갈래는 실기에서
못 봤습니다** — 확인에 쓴 계정이 `adm` 그룹에 있어서, 그 경로는 컨테이너 픽스처로만 확인했습니다.

**원자적 저장은 하드링크로 판정했습니다.** 두 서버 모두에서 같은 내용에 하드링크를 걸어 두고 저장한
뒤 링크 쪽을 읽었습니다. 쓰기 가능한 디렉터리에서는 링크에 옛 내용이 남았고(rename이 링크를 끊는다),
디렉터리 쓰기 권한을 뺀 곳에서는 링크가 새 내용을 따라왔습니다(제자리 쓰기는 링크를 끊지 않는다).
저장이 파일 모드(0600)를 잃지 않는 것도 함께 봤습니다. 두 결과가 서로 반대이므로, "원자적이라
보고하면서 제자리 쓰기하는" 구현은 이 판정을 통과할 수 없습니다. **확인은 MCP의 `fs_write`로
했습니다** — 편집기와 같은 함수를 탑니다.

Linux 클라이언트는 **창이 열리고 접속·조회까지** 확인했습니다. 파일 전송·터미널·GTK 파일 선택창은
아직입니다.

> [!IMPORTANT]
> **릴리스의 Linux 바이너리는 `libwebkit2gtk-4.1`에 링크돼 있습니다.** CI 러너가 Ubuntu 24.04라
> 거기 있는 패키지로 빌드되기 때문입니다. **22.04에서는 실행되지 않습니다** — 4.0만 있는
> 배포판에서는 [소스에서 빌드](building.md)해야 합니다.

## 미검증

| | 상태 |
|---|---|
| **Linux 클라이언트의 나머지 기능** | 창·접속·조회는 확인. 전송·터미널·GTK 파일 선택창·키체인 저장은 아직 |
| **편집기 저장의 화면 경로** | 저장 함수 자체는 두 실서버에서 원자성과 폴백까지 확인했지만, 확인은 MCP `fs_write`로 했습니다. 편집기 탭의 저장 버튼과 **연 뒤에 서버에서 바뀐 파일을 감지하는 충돌 경로**는 실기에서 눌러보지 않았습니다 |
| **RHEL·Rocky 8** | systemd 245 표 파싱 경로를 공유하므로 동작이 예상되나 확인 안 됨 |
| **Podman** | `docker` 호환 CLI라 파서를 공유하지만 실행 안 해봄 |
| **Windows 컨테이너** | 테스트한 서버에 Docker가 없었음 |
| **Windows 클라이언트의 디렉터리 다운로드** | **취약점이 실기에서 재현됐습니다(1.5.0 릴리스 `litedeck.exe`).** 백슬래시는 리눅스 파일명에서는 평범한 문자이고 Windows에서는 경로 구분자라, 서버 파일 이름이 받을 폴더 밖을 가리킬 수 있습니다. `Downloads\demo`를 대상으로 폴더를 받았더니 이름이 `..\..\PWNED.txt`인 파일이 **홈 폴더(`C:\Users\<사용자>`)에 떨어졌습니다** — 고른 폴더 두 단계 위. `scp`의 CVE-2019-6111과 같은 부류입니다. **가드(`safeLocalName`)로 막았고, 고친 빌드(dev `404b3f4`)를 같은 Windows 실기에서 확인했습니다** — 같은 함정 폴더를 받으면 전송이 거부되고 이유를 화면에 말하며 `..\..\PWNED.txt`는 홈 폴더에 생기지 않습니다. 1.5.2도 같은 코드라 픽스 전에는 똑같이 취약했습니다. 정상 전송·터미널·키체인 등 나머지 Windows 클라이언트 경로는 여전히 실행만 확인했습니다 |
| **OOM·코어 덤프 이벤트** | 분류는 systemd의 `MESSAGE_ID`로 하고 그 ID는 카탈로그에서 확인했지만, **실제 OOM이나 코어 덤프가 일어난 줄은 본 적이 없습니다.** 컨테이너에서는 커널 OOM 메시지가 호스트 저널로 가서 만들 수가 없었습니다 |
| **Windows의 모니터링 탭** | CPU 사용률·메모리·디스크 용량·가동 시간까지만 나옵니다. **CPU 분해와 코어별, 메모리 분해, 네트워크 카운터, 디스크 I/O, PSI, 실행 대기·I/O 블록, 열린 FD, inode** 는 전부 `/proc`과 `df -i`를 읽는 값이라 Windows에 원본이 없습니다. 시스템 패널의 **호스트명·CPU 명·커널 버전·시간대**도 아직 채우지 않습니다. 이벤트 탭은 뜨지 않습니다 — 이벤트 로그가 journald 자리에 대응되지만 읽는 코드가 없습니다 |
| **Windows 보안 탭의 권한 없는 계정** | 실기 확인은 관리자 계정으로만 했습니다. 항목마다 읽었는지를 따로 들고 있어 못 읽으면 그렇게 말하도록 만들었지만, 권한 없는 계정에서 실제로 어느 항목이 막히는지는 안 봤습니다 |
| **NVIDIA 카드 여러 장** | 한 장 꽂힌 실기에서 확인했습니다. 여러 장을 읽는 경로는 파서와 샘플 경계까지만 테스트로 확인했고 실기에서는 안 해봄 |
| **Compose v1·podman compose** | Compose v2 플러그인만 확인했습니다. 독립 실행형 `docker-compose`(v1)는 파일 없이 프로젝트를 다루지 못해 지원하지 않습니다. `podman compose`는 같은 경로를 타지만 실행 안 해봄 |
| **ProxyJump 실서버** | 컨테이너 두 대(경유 + 목적지)로 확인. 실제 bastion으로는 안 해봄. 다단은 미구현이고 거부합니다 |
| **macOS·BSD 서버** | 어댑터 없음. 연결하면 **파일과 터미널만** 동작하고, 나머지 탭은 이유를 화면에 적습니다 |
| **원격 → 로컬 드래그** | Wails v2에 드래그 아웃 API가 없어 구현 불가. 다운로드 버튼으로 대체 |

여기 없는 조합에서 돌려보셨다면 [이슈](https://github.com/cpprhtn/LiteDeck/issues)로 알려주세요.

## 서버 OS는 어떻게 정해지나

`uname -s`로 물어보고, 답하지 않으면 PowerShell로 `Win32_OperatingSystem`을 조회합니다. 그 응답 자체가 Windows라는 증거이면서 `Windows 10 Pro` 같은 이름도 함께 옵니다.

systemd 246 미만(Ubuntu 20.04, RHEL 8)에는 JSON 출력이 없어 **표 파싱으로 자동 전환**합니다. 버전을 감지해 형식을 고르므로 사용자가 신경 쓸 것은 없습니다.

어댑터가 없는 OS에 연결해도 **파일과 터미널은 그대로 열립니다.** SFTP와 PTY는 SSH가 직접 제공하므로 어댑터가 필요 없기 때문입니다. 나머지 탭은 어떤 OS로 확인됐는지와 함께 이유를 화면에 적습니다.

## LiteDeck이 적합하지 않은 환경

솔직하게 적습니다. 아래에 해당하면 다른 도구가 낫습니다.

| 필요한 것 | 맞는 도구 |
|---|---|
| 서버 수십·수백 대를 한 번에 | Ansible, Salt 같은 구성 관리 |
| 선언적 상태 관리 | Terraform, Ansible |
| 본격적인 원격 개발 (LSP·디버거·리팩터링) | VS Code Remote-SSH |
| GUI 앱 화면 자체가 필요 | RDP, VNC |
| SSH 외 프로토콜 (RDP·VNC·Kubernetes·Proxmox) | 여러 프로토콜을 다루는 접속 관리 도구 |
| 파일 전송만 | WinSCP, SFTP 클라이언트, `rsync` |

LiteDeck은 **SSH 하나로 닿는 서버 몇 대를, 설치물 없이, 무엇이 실행되는지 보면서** 다루는 데
집중합니다. 그 밖의 것은 위 도구들이 더 잘합니다.

## 지원하지 않는 기능

- **화면 스트리밍.** 구조화된 상태를 내놓지 못하는 대상(GUI 앱·디자이너·디버거)은 RDP가 정답이고, LiteDeck은 그 영역을 대체하려 하지 않습니다
- **구성 관리.** 선언적 상태 관리는 Ansible·Terraform의 영역입니다. LiteDeck은 그때그때 명령을 내리는 도구입니다
- **서버 상주 감시.** inotify 같은 실시간 감시는 에이전트가 필요하므로 원칙 1에 어긋납니다
- **다수 서버 일괄 관리.** 서버 2~5대를 다루는 도구입니다. 수십 대를 한꺼번에 다루는 건 다른 제품의 일입니다
